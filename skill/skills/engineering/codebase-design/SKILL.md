# Codebase Design — 共享设计词汇

这是 consult-only skill：不是独立会话，而是建立共享语言。
设计任何模块前，先读这个建立词汇；不要用"组件"、"服务"、"API"这些模糊词。

## 核心词汇

### Module（模块）

代码库中共享一个目的的一组文件/目录。
模块边界由**目的**决定，不是技术层（不能按 controller/service/dao 切）。

### Interface（接口）

模块暴露给外部的公共 API 签名。
**接口是测试表面**——接口越稳定，测试越不容易坏。
测试应该打在接口上，不是打在实现上。

### Depth（深度）

模块的深度 = 暴露给外部的能力（接口）与内部复杂度之比。
- **深模块**：大接口 + 小实现（好）
- **浅模块**：小接口 + 大实现（差，漏复杂度给调用方）

> 设计目标是让大多数模块深。浅模块是一种代码坏味道。

### Seam（接缝）

代码中可以在不修改周围代码的情况下改变行为的地方。
- **一个 adapter = 假设性 seam**（还没被测过）
- **两个 adapter = 真实的 seam**（已有多个实现）

> 新增抽象之前，先问：这里是否已有两个独立实现？如果没有，先等。

### Adapter（适配器）

把接口和实现解耦的包装层。
通过 adapter 可以 mock/stub 实现，不需要动被测代码。

### Leverage（杠杆）

某个改动对代码库其余部分的影响范围。
高杠杆 = 改动一处，撬动多处。
**先找高杠杆的模块下手**。

### Locality（局部性）

一个行为的认知负担是否集中在一处。
高局部性 = 理解这个行为只需要看很少的文件/很少的上下文。
低局部性 = 需要跳转多个文件才能理解行为（bug 的温床）。

## 设计原则

### 删除测试

如果删除一个模块，它的复杂度是否集中了？
- **是**（删除后复杂度消失）→ 好模块
- **否**（复杂度分散到其他地方）→ 坏模块（改名）

### 接口即测试表面

不要通过改内部实现来让测试通过。
如果测试需要 mock 大量内部依赖，说明接口设计不对。

### 一个 adapter = 假设，两个 = 真实

抽象之前先问：是否已有两个独立实现？
过早抽象和过晚抽象都是坑。

### 深度优先

优先让模块变深（接口宽 + 实现简），而不是拆散成多个浅模块。
