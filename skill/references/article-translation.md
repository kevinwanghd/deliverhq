# 需求语义翻译

> 来源：企业微信团队"AI代码生成率94%"经验总结。
> 核心问题：把"产品语言"变成"代码指令"——这是最容易被低估却最能体现工程价值的部分。

## 核心原则

> **真正的提效不在"AI 写代码"，而在"AI 不再需要人来当翻译"。**
> 开发者从"PRD 翻译机"转而成为"AI 的产品经理"——只在硬关卡处做决策。

## 常见翻车点

| # | 翻车点 | 真实场景 | 代价 |
|---|--------|----------|------|
| 1 | 范围错判 | PRD 段落整体在讲"后台配置"，中间一句"手机上看到的效果"被忽略 | 漏实现移动端 UI |
| 2 | 归宿不明 | 设计稿 9 张候选稿，AI 只挑 2 张做需求点 | 漏 7 个独立页面 |
| 3 | 联想扩大 | 用户说"点 A 拦截"，AI 联想"B 也应该拦" | 改了不该改的逻辑 |
| 4 | 关键词找不到 | 直接 grep "小红条" → 0 命中 | 定位失败或误命中 |
| 5 | 找错文件 | "邮件红点"翻译错位置，改了 RMail 而不是 MList | 功能完全走错地方 |

## ① 范围识别：硬关键词表

即使段落主旨在讲后端/配置/推送规则，**只要任一关键词命中**，那一段描述的功能点就**必须单独拆成移动端项**。

| 类别 | 关键词 |
|------|--------|
| 平台/端 | 手机上、手机端、移动端、iOS、Android、客户端、App |
| 原生控件/交互 | Toast、弹窗、浮层、小红条、红点、角标、下拉刷新 |
| iOS 系统组件 | 状态栏、导航栏、Home Indicator、刘海 |
| 移动端页面术语 | 输入法、键盘展开、全屏弹窗、actionsheet |

## ② 设计稿归宿

> ⛔ **RL-S04**：候选清单里每张设计稿都必须归宿明确，不允许出现"未归类"。
> 不允许用"参考图"当万能垃圾桶。

### 三类归宿

| 类型 | 说明 |
|------|------|
| 新增 | 全新页面/组件，需要开发 |
| 修改 | 现有页面的改动，需要改代码 |
| 忽略 | 与本期需求无关（如通用模板页） |

## ③ 拦截点清单（禁止语义联想）

> ⛔ **RL-S02**：任何"点击 X → 触发 Y"类拦截，X 必须有**具体引用依据**，禁止凭语义联想扩大范围。

允许的"引用来源"只有三种：

1. **设计稿标注**：`nodeId` 标注
2. **文档原文**：TAPD / 企微文档原句
3. **用户消息**：用户原话

## ④ 领域联想：5 维搜索矩阵

详见 `docs/knowledge-base/L3-语义桥/search-matrix.md`

| 维度 | 出发点 | 命中什么 |
|------|--------|----------|
| ① iOS 事件方法 | 平台标准 API | `didSelectRowAtIndexPath:` / `handleTapGesture:` |
| ② 功能语义 | 产品意图的英文同义词 | tips / banner / warning / notice |
| ③ OC 命名习惯 | 项目里的命名前缀 | `show*` / `handle*` / `on*` / `goto*` |
| ④ 协议/代理 | 谁通知谁 | `tableViewDelegate` / `<XxxDelegate>` |
| ⑤ 通知/回调 | 跨模块通信 | `XxxNotification` / `XxxCallback` |

**与 RL-S02 的边界**：联想用于搜索，引用用于决策。

## ⑤ 翻译产物

人类可读的五列表格：
| 序号 | 需求项 | 类型 | 数据来源 | 关联设计稿 nodeId |

```json
  "depends_on": ["TASK-XXX"]
}
```
