# Red Lines — Critical 红线（全局强制加载）

> **来源**：企业微信团队"AI代码生成率94%"经验
> **状态**：启动即加载，违反直接造成线上事故或严重返工

---

## 红线概览

| ID | 标题 | 触发条件 | 处置方式 |
|----|------|----------|----------|
| RL-C01 | 编译必须通过 | 退出码 != 0 | 最多3轮自修复后强制停 |
| RL-C02 | 未按阶段执行 | 跳过必要阶段 | 拒绝继续，要求返回上一步 |
| RL-C03 | 先看后写 | 未读代码就修改 | 回退到代码阅读阶段 |
| RL-C04 | 先模仿后发明 | 发明新模式/风格 | 回退到风格确认 |
| RL-C05 | 禁止修改受保护路径 | 涉及 protected_paths | 要求人工审批 |
| RL-C06 | git commit 必须同步 | 长命令误判成功 | 验证 git log -1 hash |

## RL-C01：编译必须通过

### 规则

> **唯一判据**：所有构建命令的退出码必须为 0

### 允许的自修复

- **最大轮次**：3 轮
- **自修复范围**：
  - 缺分号、标识符未声明
  - 类型不匹配、枚举漏 case
  - `#import` 找不到

### 禁止自修复（必须人工介入）

- `BUILD.bazel` 配置错误
- 链接错误
- 三方 framework 缺失
- 改动涉及多个不相关文件

### 触发报告模板

```markdown
⛔ 触发红线 RL-C01：编译必须通过

当前情形：
- 命令：{build_command}
- 退出码：{exit_code}
- 错误信息：{error_message}
- 自修复轮次：{attempt_count}/3

建议处理：
- 如果尝试 < 3：继续自修复
- 如果尝试 = 3：强制停下，报告用户
- 如果是 B 类错误：立即停下，要求人工介入
```

## RL-C02：未按阶段执行

### 规则

> **硬约束**：后一阶段的输入必须等于前一阶段的产出

### 阶段顺序

```
设计稿 → 拆解 → 定位 → 实现 → 验证 → 模拟器 → 沉淀 → 提交
```

### 禁止行为

- 用户一句话指令 → AI 跳过拆解直接改代码 → **越界**
- 跳过「定位」阶段直接写代码 → **盲目**
- 跳过「验证」阶段直接提交 → **带病上线**

### 触发报告模板

```markdown
⛔ 触发红线 RL-C02：未按阶段执行

当前情形：
- 当前阶段：{current_phase}
- 尝试进入：{target_phase}
- 缺失的前置产出：{missing_output}

建议处理：
- 返回 {current_phase} 完成必要产出
- 产出完备后再进入下一步
```

## RL-C03：先看后写

### 规则

> **必须先做**：
> 1. 查询 L2 模块 wiki，确认目标模块
> 2. 阅读完整方法，理解现有代码模式
> 3. 搜索同类分支，确认风格一致

### 禁止行为

- 未通读完整方法就开始修改
- 未搜索同类分支就发明新写法
- 未参考现有模式就创建全新的工具类

### 触发报告模板

```markdown
⛔ 触发红线 RL-C03：先看后写

当前情形：
- 尝试修改：{file_path}
- 方法：{method_name}
- 是否有完整阅读记录：{has_read}

建议处理：
1. 先完成代码阅读（使用五步定位法第4步）
2. 确认理解了现有模式后再继续
```

## RL-C04：先模仿后发明

### 规则

> **发明禁令**：禁止发明项目中不存在的模式或风格

### 必须参照

- L2 模块 wiki 里的文件登记表
- 同一模块内其他文件的实现风格
- 相似功能的实现模式

### 禁止行为

- 为同类功能发明不同的命名风格
- 在已有 Service 的情况下创建新的 Helper 类
- 不参考现有代码创建全新的工具类

### 触发报告模板

```markdown
⛔ 触发红线 RL-C04：先模仿后发明

当前情形：
- 新增模式：{new_pattern}
- 是否有同类参照：{has_reference}

建议处理：
1. 先搜索项目中现有的相似实现
2. 参照现有风格进行开发
3. 如确实需要新模式，请在 human-decisions.md 中记录理由
```

## RL-C05：禁止修改受保护路径

### 规则

> **受保护路径**定义在 `dir-graph.yaml` 的 `protected_paths` 字段

### 默认受保护路径

```yaml
protected_paths:
  - ../configs/**      # 配置文件
  - ../secrets/**     # 密钥文件
  - ../.env           # 环境变量
  - ../node_modules/** # 依赖（特定项目）
```

### 禁止行为

- 未经人工审批修改配置文件
- 未经人工审批修改环境变量
- 未经人工审批修改密钥文件

### 触发报告模板

```markdown
⛔ 触发红线 RL-C05：禁止修改受保护路径

当前情形：
- 尝试修改：{file_path}
- 是否在 protected_paths 中：{is_protected}
- 是否有人工审批：{has_approval}

建议处理：
1. 暂停修改
2. 向用户说明需要修改的文件
3. 获得明确批准后再继续
```

## RL-C06：git commit 必须同步执行

### 规则

> **唯一成功判据**：`git log -1` hash 是否更新

### 问题场景

- 长跑命令被 terminal 置后台
- stdout 被截断
- AI 误判成功

### 验证流程

```bash
# 记录 commit 前的 hash
BEFORE=$(git log -1 --format=%H)

# 执行 commit
git commit -m "..."

# 验证 hash 是否更新
AFTER=$(git log -1 --format=%H)
if [ "$BEFORE" != "$AFTER" ]; then
    echo "✅ commit 成功"
else
    echo "❌ commit 失败，hash 未更新"
fi
```

### 触发报告模板

```markdown
⛔ 触发红线 RL-C06：git commit 必须同步执行

当前情形：
- 执行前 hash：{before_hash}
- 执行后 hash：{after_hash}
- 是否更新：{updated}

建议处理：
1. 检查 git commit 命令输出
2. 验证 .git/COMMIT_EDITMSG 是否存在
3. 重新执行 commit 或解决冲突
```
